# Vork 系统设计

**日期：** 2026-09-14  
**状态：** 已批准，可进入实施计划阶段  
**仓库：** `/Users/maple/code/repo/VorkBot`

## 1. 产品定义

Vork 是一款可自托管的桌面应用，用于创建能够通过云电脑完成真实工作的持久化 AI Bot。每个 Bot 都有名称、角色、指令、记忆、工具、文件、浏览器会话和任务历史。用户通过对话与 Bot 协作；即使桌面客户端关闭，任务仍会在腾讯云 Ubuntu 服务器上继续运行。

第一版仅供单用户使用。用户可创建任意数量的 Bot，但同一台共享云电脑容器最多提供三个并发执行槽；在初始 4 核 8 GB 服务器上，浏览器重任务最多同时运行两个。

Vork 是通用 Bot 平台，而非某个垂直业务工具。扩展能力来自结构化工具、记忆、Skills，以及后续加入的例程和 Bot 间任务委派。

## 2. 目标

- 提供经过签名和公证的 macOS Electron 客户端。
- 通过对话创建和配置 Bot，不使用传统创建表单。
- 让 Bot 使用云端持久化 Chromium、终端和文件系统。
- 桌面客户端关闭后，任务继续运行。
- 实时返回进度、工具活动、审批请求和结果。
- 用户可查看、暂停、取消、批准或接管任务。
- 持久保存 Bot 身份、相关记忆、浏览器登录状态、文件和可恢复任务状态。
- 将成功任务总结为可审核、可版本化的 Skill 草稿。
- 在模型之外强制执行资源、费用、时间、权限和副作用限制。

## 3. 第一版不包含的内容

- iOS、Android、Windows 和 Linux 客户端。
- 将纯 Web 客户端作为主产品。
- 云电脑容器中的完整 GNOME/KDE 桌面。
- 云端运行 Windows/macOS 原生应用。
- 本地大模型推理或 GPU 任务。
- 每个 Bot 独立容器。
- 公开多用户 SaaS、计费、团队管理和企业身份系统。
- 公共插件、连接器或市场。
- 面向用户开放的多 Bot 群聊和任务委派。
- Bot 内部临时创建规划、执行和审核 Agent 的多层结构。
- 未经审核自动启用生成的 Skill。
- 无限制 Shell 权限或无限执行时长。

## 4. 用户体验

### 4.1 应用框架

- 左侧边栏展示搜索、Bot/对话列表、`+` 新聊天按钮，以及底部用户身份。
- 点击用户头像或名字后，显示任务队列、Skills、文件、模型凭据和系统设置等管理入口。
- 中央区域展示当前对话。
- 云电脑实时画面默认隐藏，仅在用户点击对话标题栏中的电脑入口后展开。
- 审批请求同时出现在对话中和 macOS 系统通知中。

### 4.2 新聊天与创建 Bot

Vork 使用已在本机 Grok Bot 中核实的交互：

1. 点击左侧 `+` 进入新聊天。
2. 主区域顶部变成收件人搜索/选择框。
3. 收件人列表第一项是“创建新 Bot”；群聊功能开放后第二项为“创建群聊”，其后是已有 Bot。
4. 选择“创建新 Bot”后，系统立即创建临时 Bot 并进入空白对话。
5. 用户通过对话描述名称、职责和工作方式；Bot 将内容整理成配置建议。涉及重要权限时必须获得用户确认。

第一版不提供独立 Bot 创建表单。

### 4.3 云电脑查看与接管

实时执行面板默认关闭，展开后可显示：

- Chromium 实时画面或截图流。
- 当前工具和执行步骤。
- 终端输出。
- 新建或变更的文件。
- 审批请求。
- 暂停、取消、接管和交还控制权操作。

浏览器控制采用互斥状态机：

```text
agent_control -> handoff_pending -> human_control -> agent_control
```

用户接管后，Agent 不得继续点击或输入。

## 5. 系统架构

```text
macOS Electron 客户端
        |
        | HTTPS + WebSocket/SSE
        v
API 与实时网关
        |
        +--> PostgreSQL
        +--> Redis/BullMQ
        +--> Agent Worker
                  |
                  v
             权限与审批层
                  |
                  v
          共享云电脑容器
          +-- 执行槽 1
          +-- 执行槽 2
          +-- 执行槽 3
          +-- 持久化卷
```

模型不能直接控制 Docker 或宿主机，只能产生通过 Schema 校验的结构化工具调用。权限层在云电脑执行前决定允许、拒绝或暂停等待用户审批。

### 5.1 仓库结构

```text
apps/
  desktop/       Electron + React + Vite
  api/           Fastify HTTP API 与实时网关
  worker/        Agent Runtime 与任务消费者
  computer/      浏览器、终端、文件控制服务
packages/
  contracts/     API、事件和工具 Schema
  database/      PostgreSQL Schema 与数据访问
  agent-core/    Agent 循环、上下文、检查点和预算
  tools/         浏览器、终端、文件、记忆和消息工具
  policy/        权限、审批和敏感数据规则
  shared/        公共类型、错误模型和日志
infra/
  docker/        镜像与运行配置
  compose/       本地和服务器部署
```

第一版全栈统一使用 TypeScript；所有跨进程契约必须在运行时校验，不能只依赖 TypeScript 类型。

## 6. Electron 客户端

客户端分为三层安全边界：

```text
Electron Main
  +-- 窗口与生命周期
  +-- 自动更新
  +-- macOS 通知
  +-- Keychain 凭据
  +-- 原生文件选择和下载

Preload Bridge
  +-- 范围严格、类型明确的 IPC API

React Renderer
  +-- Bot 与对话
  +-- 任务事件流
  +-- 审批
  +-- 文件预览
  +-- 云电脑查看与接管
```

必须启用 `contextIsolation: true` 和 `nodeIntegration: false`。Renderer 不可直接访问 Node.js、文件系统和 Shell。Preload 只暴露白名单 IPC。外部链接交给系统浏览器。远程内容不获得 Electron 权限。API Token 存入 macOS Keychain，不存放在 Renderer 状态或明文配置中。

## 7. 任务生命周期与 Agent Runtime

### 7.1 任务生命周期

```text
用户消息
  -> 创建 queued 任务
  -> 调度器获取执行槽租约
  -> Agent 加载受限上下文并提出下一步动作
  -> 权限层校验
  -> 工具执行，或任务等待审批
  -> 保存观察结果和检查点
  -> Agent 继续、完成、失败或报告阻塞
  -> 保存结果和记忆建议
  -> 释放执行槽
```

任务状态包括：`queued`、`running`、`waiting_approval`、`paused`、`completed`、`failed` 和 `cancelled`。

所有重要状态变化和工具结果都追加到具有单调序号的事件流。客户端重连时携带最后事件游标，以补回断线期间的事件。

### 7.2 单层 Bot Runtime

第一版中，一个 Bot 使用一个受控模型循环完成一项任务：

```text
上下文 -> 模型 -> 结构化动作 -> 权限层 -> 工具 -> 观察结果 -> 模型
```

“单层”不限制持久 Bot 数量，只是不在 Bot 内部临时创建多级 Agent。未来通过父任务、根任务和交接协议支持 Bot 间协作。

模型每轮只能返回一个类型化动作，例如：

- `browser.*`
- `terminal.*`
- `file.*`
- `memory.*`
- `message.*`
- `approval.request`
- `task.complete`
- `task.fail`

每个任务必须限制模型轮数、工具调用次数、运行时长、Token/费用预算、命令时长、输出大小、连续失败次数和重复动作次数，并在每个动作之间检查取消信号和租约心跳。

### 7.3 上下文组装

每轮模型调用只加载：

- Bot 角色和长期指令。
- 当前任务目标和完成标准。
- 最近对话消息和压缩摘要。
- 检索到的相关、有来源的记忆。
- 当前浏览器、终端和工作区状态。
- 数量受限的近期工具结果。
- 可用工具 Schema 和当前权限约束。

不得在每轮重新发送完整对话和事件历史。

## 8. 共享云电脑

第一版为单个账户运行一个持久容器：

```text
cloud-computer container
  +-- 进程监管器
  +-- 每个活动执行槽一个 Chromium 进程/Profile
  +-- Xvfb + 轻量窗口管理器
  +-- Playwright 控制服务
  +-- PTY 终端网关
  +-- 工作区文件服务
  +-- /workspace/bots/{bot_id}
  +-- /workspace/shared
  +-- /browser-profiles/{slot_id}
```

Xvfb 和轻量窗口管理器仅用于渲染 Chromium 与支持人工接管，不构成通用桌面环境。

容器以非 root 用户运行，禁止 `--privileged`、Docker Socket 和宿主机敏感挂载。CDP、PTY 和文件服务端口不得公开。系统限制 CPU、内存、磁盘、进程数、命令时长和输出大小；云电脑 API 只允许经过服务认证的 Docker 内部网络访问。

工作区、浏览器 Profile 和任务产物分别使用持久化卷；PostgreSQL 数据不存入云电脑容器。

### 8.1 执行槽

- Bot 数量不限。
- 最多三个任务同时占用执行槽。
- 4 核 8 GB 服务器最多同时运行两个浏览器重任务。
- 每个执行槽拥有独立 Chromium、浏览器 Profile、PTY 和任务工作区。
- 浏览器崩溃只重启对应执行槽。
- 宿主机内存达到初始 80% 高水位后暂停领取新浏览器任务。

## 9. 浏览器观察与恢复

页面理解以 DOM 和可访问性树为主，截图与视觉模型作为补充。观察结果包含页面 ID、URL、标题、加载状态、语义化交互元素、近期截图、下载记录和精简后的控制台/网络错误。

模型引用短期有效的语义元素标识。页面跳转或 DOM 明显变化后，旧标识自动失效。定位优先级为：

1. 可访问性角色和名称。
2. 稳定测试属性或应用属性。
3. 文本与 DOM 关系。
4. 视觉候选区域。
5. 屏幕坐标。

动作必须通过后置条件验证，不能将“点击成功”等同于业务完成。元素过期时重新观察；页面异常采用有限刷新/重开；浏览器崩溃执行槽内重启；登录失效、CAPTCHA 和 2FA 要求用户接管。

可能产生副作用且结果不确定的调用使用：

```text
prepared -> executing -> uncertain -> verified_success | safe_to_retry | failed
```

`uncertain` 状态必须先检查真实结果，再决定是否重试。

## 10. 数据模型

核心实体包括：

- `users`
- `bots`
- `conversations`
- `conversation_members`
- `messages`
- `tasks`
- `task_events`
- `tool_calls`
- `approvals`
- `artifacts`
- `memories`
- `execution_leases`
- `browser_profiles`
- `skills`
- `skill_versions`
- `skill_proposals`
- `routines`
- `task_handoffs`
- `audit_logs`

对话与任务分离：一条消息可以触发任务，一个任务可以生成多条消息和事件。任务事件只追加不修改。大型截图和文件存放在数据库外，数据库只记录路径、哈希、大小和 MIME 类型。Secret 不得进入普通事件。

Redis 保存队列、锁、租约和临时在线状态；PostgreSQL 是业务事实来源。

通过 `parent_task_id`、`root_task_id`、`assigned_bot_id` 和 `task_handoffs` 预留多 Bot 能力。内部可定义 `bot.delegate` 和 `bot.message` 契约，但第一版不向模型或客户端开放。

## 11. 记忆

记忆分为：

- 身份记忆：经用户确认的角色、行为和长期规则。
- 事实记忆：带来源和置信度的偏好及项目背景。
- 工作记忆：当前任务摘要和未解决状态，任务结束后压缩或清除。

每条长期记忆记录 Bot、类型、内容、来源任务/消息、置信度、敏感级别、创建时间、最近使用时间和替代关系。密码、Cookie 和 API Key 属于凭据，不属于记忆。

模型只提出记忆建议；记忆服务负责去重和冲突检查。普通偏好按策略保存，敏感信息必须确认。用户能够查看、修改、替代或删除长期记忆。

第一版使用 PostgreSQL 全文搜索和 `pgvector`，不引入独立向量数据库。

## 12. Skills 与例程

Skill 是可版本化的复用流程：

```text
skills/{skill-name}/
  SKILL.md
  manifest.json
  scripts/
  references/
```

Manifest 描述版本、适用任务、输入输出、所需工具和域名、权限/审批、资源限制、来源和完整性哈希。实际权限是 Skill、Bot 和任务策略的交集。

Vork 支持自动总结经验，但不会自动启用：

```text
成功任务
  -> 提取轨迹
  -> 删除误操作、偶然等待和 Secret
  -> 参数化具体值
  -> 总结语义步骤、恢复方式、权限和成功条件
  -> 生成 Skill 草稿
  -> 沙箱回放或验证
  -> 用户审核
  -> 发布版本
```

第一版提供“保存为 Skill”，并在相似任务多次成功后主动建议生成草稿。后续版本可以根据成功率建议修订，或暂停连续失败的 Skill 版本。

例程预留为“触发器 + Bot + 任务模板 + 预算 + 策略”。第一版定义存储和创建任务的边界，但不在客户端开放定时运行界面。

## 13. 权限与审批

- 低风险：读取网页、搜索工作区，可以自动执行。
- 中风险：安装软件、首次访问域名，按配置策略处理。
- 高风险：发送、提交、删除、上传敏感数据和金融操作，必须明确审批。
- 禁止：修改宿主机、访问 Docker Socket、提权、关闭审计、突破工作区或网络策略。

所有工具输入都要经过 Schema 校验。文件路径规范化后必须位于允许目录。终端进程以非 root 身份运行并追踪完整进程树。结构化日志自动脱敏。

## 14. 错误处理与可观测性

- 客户端断线不取消云端任务。
- 重连时从最后确认的事件游标恢复。
- Worker 重启后从持久检查点和过期租约恢复。
- 云电脑不可用时暂停任务，避免模型在无观察结果时继续规划。
- 模型超时采用有限指数退避，可切换到已配置的备用供应商。
- 用户可见错误必须给出重试、登录、接管或取消等明确操作。
- 日志通过 `request_id`、`task_id`、`tool_call_id` 关联并自动脱敏。

监控指标至少包括 CPU、内存、磁盘、队列长度、执行槽状态、任务成功率、模型费用、审批等待时间和浏览器崩溃次数。

## 15. 测试

测试分为四层：

1. 单元测试：任务状态机、权限策略、预算、记忆冲突和 Skill 草稿。
2. 契约测试：Electron IPC、HTTP/实时 API、事件和工具 Schema。
3. 集成测试：真实 PostgreSQL、Redis、Docker 和受控测试网站。
4. 端到端测试：创建 Bot、浏览器任务、终端、文件、审批、接管、取消和崩溃恢复。

常规自动化测试使用确定性的假模型产生固定工具调用，另设少量真实模型冒烟测试。浏览器测试使用自建受控网站，不依赖变化频繁的第三方页面。

发布验收场景：

1. 研究 Bot 访问多个受控网站并生成带来源的 Markdown 报告。
2. 开发 Bot 通过终端修改示例工作区并运行测试。
3. 文件 Bot 整理上传文件，并在覆盖或删除前申请审批。
4. 服务重启后，Bot、对话、浏览器 Profile、文件和可恢复任务仍然存在。

## 16. 部署

初始服务器为腾讯云 Ubuntu，4 核 CPU、8 GB 内存、512 GB 存储。模型通过外部 API 推理，无需 GPU。

Docker Compose 运行 Caddy、API、Worker、PostgreSQL、Redis 和云电脑容器。公网只开放：

- `443`：HTTPS 和实时通信。
- `22`：SSH，仅允许用户固定 IP 或堡垒机访问。

PostgreSQL、Redis、Chromium CDP、远程画面、PTY、文件服务和 Docker API 均不得暴露公网。Caddy 负责 TLS 和已认证的 HTTP/实时连接反向代理。

数据库每日备份；工作区和浏览器 Profile 创建加密快照，并定期测试恢复。选定腾讯云区域前必须验证模型 API 和目标网站的网络可达性；大陆区不稳定时优先选择中国香港或其他合适区域。

## 17. 第一版完成标准

- 已签名和公证的 macOS Electron 应用安全连接服务器。
- 对话式创建 Bot 和已确认的简洁界面可端到端使用。
- 三个执行槽安全调度，浏览器重任务不超过两个。
- 浏览器、终端和文件工具经过权限层执行，并生成持久任务事件。
- 审批、接管、取消、断线重连和重启恢复正常。
- Bot 身份和带来源的记忆重启后仍然存在。
- 成功任务可以生成供用户审核的 Skill 草稿。
- 四个验收场景在全新部署中通过。
- 运维文档覆盖安装、Secret、备份、恢复、升级和故障处理。
